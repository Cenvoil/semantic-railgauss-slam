### 3.1b ⚠ 修掉的一个真 bug：LiDAR 锚里写进了负深度

**根因（追到代码根源）**：`proj_canon.project()` 的 docstring 明确写着 **"不裁剪"** ——
它不做 `z>0.3` 过滤，直接返回全部点的 `(z,u,v)`。
我原先**误以为它已过滤**（脚本注释就是这么写的），于是

```python
zl_map[vi, ui] = zl          # 把相机后方的点也写了进去
```

把相机后方的点（每帧 17.2% 的点、深度低至 −52 m）也写进了深度图。

**实测影响面**：全部 100 帧的 `valid==2` 都含负深度，共 **6337 px / 5,563,253 = 0.114%**。

**修法**：写入前显式加 `z>0.3` 掩膜；并加**硬断言**（`assert not (fused[vm] <= 0).any()`），
让这类问题下次当场被拦住，而不是靠事后诊断。

**修后复核**：

| | 修复前 | 修复后 |
|---|---|---|
| 含负深度的帧数 | **100 / 100** | **0 / 100** |
| `valid==2` 最小深度 | **−52.26 m** | **+3.98 m** |
| s 中位 | 1.8186 | 1.8186（不变） |
| holdout absrel 中位 | 0.0621 | 0.0623 |
| LiDAR 锚像素数 | 5,563,253 | 5,556,921（少 6332 = 被剔除的负值点） |

已验证修法**不误删真实近场**：过滤后入画点 min=4.81 m（不是贴着 0.3 的边界值），
且 1~5 m 区间只有 3 个点 —— 5.1 站场画面里本就没有很近的地面。
主干数字不变，说明修复只影响那 0.114% 的负值像素。

### 3.2 独立核验（三条腿，刻意避开"用写入值验证写入值"）

| 腿 | 方法 | 结果 | 判读 |
|---|---|---|---|
| 1 | 轨面像素：内容定律距离 / 深度图值 | **0.9926**（逐帧 0.940~1.030） | ≈1.0，自洽 |
| 2 | 地面像素反推相机高 `h_imp = d·(v−VH)/fy` | **3.5117 m** vs 官方 3.5098 m，**比值 1.0005** | 尺度无偏 |
| 3 | 直方图 + CAP 堆积 | 单峰在 10~40 m（占 50%），≥119.5 m 占 0.0000% | 无人造远场壳 |

**腿 2 最硬**：它只用「深度图 + 内参 + 地平线行」，**完全绕开 LiDAR 外参**，
是第三方基准。数学上 `h_imp = h_true / r` ⇒ 隐含 **r = 0.9995**（深度尺度无偏）。

> 对照 1.2：MEMORY 记其地面反推给出 `r ≈ 0.573 + 0.0318·Z`（约 31 m 处饱和），
> 需靠 `gk` 组乘 1.0448 校正。**5.1 不需要这一步。**

### 3.3 关于"乘数缩放"（用户交付目标 ③ 的第三段）

**本次不施加任何乘数**（`SCALE=1.0`）。理由：
1.2 的 1.0448 是**用 1.2 自己的 LiDAR 轨距独立标定**得到的（1.548 标称 vs 估计 20.33 m），
**弯道/车站场景的轨面几何与标定场不同，沿用 1.2 的值没有任何依据**。
若 5.1 后续要缩放（`gk` 类实验），必须用 5.1 自己的轨距重新标定 ——
本轮的 `depths/` 是干净的未缩放底稿，可直接乘。

### 4.1c 照抄 1.2 脚本会踩的三个坑（都已实测抓出并修）

1. **⚠ 通道序：5.1 是 RGB，1.2 脚本的 `[::-1]` 反转在 5.1 上是错的。**
   1.2 版对「旧图缺的类」用 `info色[::-1]`，那只在旧图是 BGR 时成立。
   5.1 实测：类 3 旧图 (0,0,142) == info **RGB** (0,0,142)、类 18 旧图 (220,220,0) == info RGB，
   两类都唯一匹配 RGB、匹配 BGR 的为 0 ⇒ 用 RGB。
   **5.1 的 SRC 旧图只标了 5 个类**，其余 24 个类全靠 info 色回退 ⇒ 这个错会染红 24/29 个类。
   修法：**按实测自动裁决**（数「匹配 RGB 的类数」vs「匹配 BGR 的类数」）而非写死结论。
2. **L4 npy 是 `uint16`**，1.2 版的 `assert dtype == uint8` + `astype(np.uint8)` → 存成 `L` 模式，
   而 5.1 的 SRC 旧图是 `I;16`。已改为按原 dtype 存、模式与 SRC 一致。
   （加载器 `imageio.imread` 两种模式都能读成整型、`INTER_NEAREST` 不产生新 id，
   所以这是**规范性对齐而非 bug**，但仍按铁律 ⑫ 读代码确认过。）
3. **脚本自检的「软链数」口径错**：`os.listdir` 沿软链列的是子项，数子项里的软链恒为 0。
   已改为 `os.path.islink(目录本身)` + 单独打印顶层软链核对。

### 4.2 修掉的两个真实 bug（1.2 原版代码在 5.1 上暴露）

1. `build_l1v9.py:156` — `c3u, c3v = project(ctr)[0][0] if m.sum() else (None,None)`
   `project()` 内部已按 `z>0.3` 过滤，返回的 `uv` 可能为空；而 `m.sum()` 计的是**过滤前**的点数。
   5.1 的 `train` 类 cuboid 中心落在相机后方 → `m.sum()>0` 但 `uv` 为空 → **IndexError**。
   修为「用返回值长度 `len(uv)` 判据」。
2. `build_l1v9.py:173` — `if m.sum() < 8: continue` 同样用错判据（cuboid 角点部分在后方），
   后面 `ConvexHull(uv)` 会抛错。修为 `if len(uv) < 8`。

**1.2 从未触发这两个 bug**（其 cuboid 都在前方）⇒ 这是"沿用旧代码"会漏掉的，
只有换场景才会暴露。
